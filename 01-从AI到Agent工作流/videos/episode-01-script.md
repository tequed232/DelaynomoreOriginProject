## 第一节：先谈谈 AI 是否正在代替我们思考（00:55—02:15）

**画面**
- 左侧：用户向聊天 AI 提问，AI 返回建议。
- 右侧：用户给 Agent 下达任务，Agent 读取资料并生成执行计划。
- 中间出现提示：`能执行，不等于应该无条件授权。`

**旁白**

在开始操作之前，我们先明确一件事：AI 能替我们处理很多任务，但这不代表我们应该把所有判断都交给 AI。

例如，让 AI 整理资料、生成代码初稿、检查 Markdown 格式，这些工作通常比较适合交给 AI 辅助完成。

但涉及账号权限、数据删除、资金、隐私或生产环境时，我们必须清楚它准备做什么，并且在执行前确认风险。

所以，今天这套工作流的目标不是让 AI 无限制地替我们做决定，而是让它在明确的目标和权限范围内完成任务。

**屏幕文字**
- 明确目标
- 控制权限
- 检查执行结果
- 人负责最终验收

这里以腾讯 WorkBuddy 为演示对象。我们先确认当前版本是否支持自定义 API 或兼容接口，再按照它实际提供的配置入口填写信息。

## 第六节：接入 GitHub MCP（09:45—12:20）

**画面**
- 展示 MCP 架构图：Agent / Host → MCP Client → MCP Server → GitHub API。
- 展示实际使用的 GitHub MCP Server。
- 展示授权范围，但隐藏 Token。

**旁白**

最后，我们来接入 GitHub MCP。

MCP 是一种让 AI 应用与外部工具、数据服务进行标准化交互的协议。

在这里，GitHub MCP Server 会把它实现的部分 GitHub 能力提供给支持 MCP 的客户端。

接入之后，Agent 就有机会在授权范围内读取仓库信息、查看 Issue 和 Pull Request，具体能做什么取决于所使用的 Server 及其权限配置。

这里有一个很重要的安全原则：先从只读权限开始。

例如，我们可以让 Agent 查询仓库信息、读取某个 Markdown 文件、整理近期 Issue。确认这些操作正常后，再考虑是否开放创建评论或提交修改等写入能力。

不要为了方便直接给 Agent 全部仓库权限。

**操作**
1. 展示所选 GitHub MCP Server 的官方仓库。
2. 阅读配置和认证说明。
3. 按官方方式完成认证。
4. 在客户端启用 MCP Server。
5. 查看工具列表。
6. 测试读取指定仓库信息。
7. 测试读取指定文件。
8. 展示未授权写入操作需要确认的原则。

**屏幕文字**
- 先只读。
- 最小权限。
- 写入前确认。
- Token 不要公开。

## 第七节：把所有组件串起来（12:20—13:35）

**画面**
展示完整工作流：

```text
用户提出任务
      │
      ▼
DeepSeekHarness
      │
      ├── 模型 API
      ├── Plugins
      ├── Skills
      └── GitHub MCP
              │
              ▼
        Agent 执行计划
              │
              ▼
        用户检查与授权
              │
              ▼
        执行并返回结果
              │
              ▼
        用户验收
```

**旁白**

到这里，我们就把今天涉及的几个部分串起来了。

模型 API 提供模型能力，DeepSeekHarness 组织运行过程，Plugins 扩展宿主能力，Skills 提供可复用的任务方法，而 GitHub MCP 则让 Agent 能够按照授权访问 GitHub。

它们并不是互相替代的关系，而是在一个工作流中承担不同职责。

真正重要的不是安装了多少插件，而是你是否清楚每个组件的用途、权限和边界。
